# 模块审计手册

**判据清单、探针与报告格式的唯一真相。** 触发方式见
`.claude/skills/module-audit/SKILL.md`（那只是个入口，不复制本文件的内容）。

> **本文件不是 XFramework 那份的翻版。** 那份 226 行，判据大量涉及异步、生命周期、
> 并发、对象池——本包是一套**纯编辑期的 IMGUI 管线**，那些类别基本不适用。
> 这里按「本包真正会出的问题」重写，保留了它的报告格式与归档落点表。

---

## 一、这份手册解决什么

审计是「找潜在问题 + 与成熟实现对照 + 给改进建议」。它要防的是两件事：

1. **只找到显然的东西。** 没有固定清单时，人会一遍遍检查自己熟悉的那几处。
2. **结论无处可去。** 找到的问题写完就散，下一轮重新发现一遍。

所以本文件给**清单**（第三节）与**落点**（第五节）。

---

## 二、一次审计的四步

1. **普查**：范围是哪个部分？文件清单、公开面、依赖方向、消费方（谁在用它的什么）、
   测试覆盖到哪。范围大时用 Explore 子代理并行——这一步不需要判断力，只需要「全」。
2. **判据逐类扫**：按第三节清单逐类问。不必每类都命中，但**每类都要留下
   「扫过了、无问题」的痕迹**——否则报告无法区分「没找到」与「没看」。
3. **定向验证**：可疑点必须落到证据上。
   - 只有编译器知道答案的 → **写独立复现程序编译验证**（重载决议、二义、cast 行为），
     并配一个**负向控制**证明验证程序真有判别力
   - 只有 Unity 知道答案的 → **在编辑器里实测**，把日志原话抄进结论
     （本包已有两例：`GetIterator` 实例复用、asmdef 无脚本被跳过）
   - 只有仓库知道答案的 → **跑门禁**
   - 纪律见 [Workflow.md](Workflow.md) §三：「改前必红」与「区分实测与推理」
4. **报告与拆分**：按严重度排序 + 每条给理由 + **「不该做」也写成结论** +
   第三方对照表 + 标明实测/推理；然后按提交纪律拆原子提交。

## 三、缺陷类清单

### A. 绘制器链契约

- 链条是否**永不为空**？每个节点的 `Chain` 是否都有末端？
- `CallNext` 越界是否抛异常（而不是静默）？
- 游标在**异常**与**重入**之后是否被恢复？（`Draw` 用 `try/finally`）
- 同权重绘制器的顺序是否**确定**？（序号兜底不能省，`List.Sort` 不稳定）
- 排序依据是「权重升序 + 序号」吗？小 = 外层这条有没有被反过来？
- 一个属性挂**多个同类型特性**时，是否每个特性实例各配一格？（按绘制器去重会吞掉第二个）
- `DrawerChainEntry` 携带的是触发它的**那个特性实例**，而不是只带绘制器类型？

### B. 状态归属

- 绘制器里有没有**可变字段**？（只允许 `readonly` 的不可变字段）
  这是本架构的硬约束，违反的症状是「展开一个、全都展开了」
- 每属性状态是否都走 `PropertyState`？（`GetOrCreate<T>` / `Get<T>`）
- 静态字段有没有被当缓存用？域重载会清掉它们——清了之后还能正确重建吗？
  （`DrawerTypeRegistry` 就是靠这个：静态缓存 + 域重载后自动重扫）
- fixture 是否复位了它触碰的静态门面？（`DrawerTypeRegistry.Reset()`）

### C. 分组装配

- **不变量**：每个分组节点上的分组特性是否满足 `GroupID == node.Path`？
  破了这条，绘制器就无从判断自己在画哪一层
- 分组节点是否落在**其首个成员出现的位置**？（未分组字段不该被挤到末尾）
- 祖先节点是否被正确**合成**？合成时是否用了 `CloneForPath`（保住子类字段）
  而不是重新构造？
- 同组多次声明时，`Combine` 的规则是什么？**是否累加**？（Order 累加会让
  「给分组多加一个字段」意外改变排序位置）
- 同层分组按 `Order` 重排时，是否**没有动未分组成员的相对位置**？
- 每个属性的特性是否是**独立副本**？一个类级特性实例若被多个成员共享，
  改一处会串一片
- 路径查找用的是**完整路径**还是显示名？嵌套分组的路径是全路径，显示名只是末段

### D. 值后端与序列化语义

- 值入口持有的是**稳定的** `SerializedProperty` 实例吗？
  `GetIterator()` 返回的是同一个实例、`NextVisible` 就地改写它——
  存下来会让所有节点共享一个对象（症状：每个字段显示同一个值）
- `ApplyModifiedProperties` 与 `Update` 的配对位置对不对？少了任何一个，
  Undo、预制体覆盖、场景标脏、域重载后取值都会出问题
- 多对象编辑下 `hasMultipleDifferentValues` 的路径是否处理了？
  取值时抛异常还是挑一个目标？**不能挑一个冒充**
- 读写的类型分支是否覆盖了 `SerializedPropertyType` 的常用项？未覆盖的是抛异常
  还是静默返回默认值？（应当抛）
- **第二套后端**（`ReflectedValueEntry`）的只读契约被守住没有？`SetValue` 必须恒抛；
  `SerializedProperty` 为 null **当且仅当** `IsUnityBacked` 为 false
- **反射成员的取值走的是单次读取 API 吗**？「先问 `HasMultipleDifferentValues`
  再问 `GetValue`」会把用户的 getter 每帧读两轮——那条 API 存在的唯一理由就是这个
- 目标列表是 `object[]` 而不是 `Object[]` 之后，判空**是否都过了 `TargetObjects.IsAlive`**？
  裸写 `!= null` 对已销毁的 Unity 对象会返回错误的答案（引用比较），
  而这条语义以前是 `Object[]` 白送的

### E. 性能与 GC

- 每帧路径（`Draw`、`DrawChildren`、`OnInspectorGUI`）里有没有 LINQ、
  闭包分配、字符串拼接？
- `GUIContent` 是否被复用？（默认标签缓存在节点上）
- 绘制器实例是否**共享**而非每属性新建？
- 反射是否只发生在构建期？绘制路径里出现反射就是问题。
  **包括取值**：反射成员与反射条件都必须在构建期编译成委托
  （`ReflectedAccessor`、`TryCreateBooleanReader`、`MethodInfo.CreateDelegate`），
  绘制期只剩委托调用。`MethodInfo.Invoke` 出现在每帧路径上同样是问题
- 每帧路径上有没有**装箱**？`ReflectedAccessor.Read` 会装箱（只读展示每帧本来就要拼字符串，
  可接受）；条件求值那条**不行**，它走的是强类型读取器
- `PropertyState` 的附加状态袋是否按类型复用（`GetOrCreate`）而不是每帧新建？

### F. 扩展点契约

- 使用方在自己项目里写的绘制器，**无需注册**就能被发现吗？
  （`DrawerTypeRegistry` 扫全部已加载的编辑器程序集）
- 没有公开无参构造函数的绘制器，是被跳过并告警，还是让整个扫描失败？
  （跳过——一个写坏的第三方绘制器不该让整个 Inspector 瘫掉）
- Runtime 侧是否仍然零 Unity 依赖？（`dotnet build Tests.Native` 会直接回答）
- 末端绘制器的 `CanDraw` 是否恒为 `false`？（返回 true 会被重复加进链）

### G. 文档与门禁

- 三条门禁是否都过？见 [Workflow.md](Workflow.md) §一
- 包内 README 的「已知限制」是否与实际行为一致？（不许诺做不到的事）
- XML 注释里有没有未转义的泛型尖括号或裸 `&`？未转义触发 CS1570 会让
  **整条注释被编译器丢弃**，且块内 `cref` 一律不再被检查——死链因此隐形
  （表现为「**没有**告警」而不是「有告警」）
- 文档有没有指向**根本不存在的东西**（已改名/已删的成员）？这属于内容问题，
  先确认真实 API 再改，不要机械替换

## 四、报告格式

```
## 结论摘要
<按严重度排序，每条一句话>

## 逐条

### [严重度] 标题
- **现象**：会看到什么
- **根因**：
- **证据**：实测 / 推理（**必须标明**）
- **建议**：
- **落点**：见第五节

## 扫过但无问题的类别
<逐类列出——这是「没找到」与「没看」的区别>

## 第三方对照
| 维度 | 本包 | Odin | 说明 |
```

严重度用三档：**会出错**（用户可见的错误行为）、**会难维护**（现在没错，改动时容易踩）、
**建议**（更好但没有必须做的理由）。

## 五、结论归档

**按收件人分流，一处只写一份真相：**

| 结论性质 | 落点 |
|---|---|
| 使用方要知道的边界（「这个特性有个坑」） | `Assets/XInspector/Runtime\|Editor/README.md` |
| 接口承诺到哪为止 | 同上 |
| 「为什么是 A 而不是 B」的取舍 | 同上；若只有维护方关心则进 `Modules/` |
| 已评估未采纳、已否决形状 | `Documentation/Modules/<模块>.md` |
| 还没做的候选（该不该做、边界画在哪） | `Documentation/Roadmap.md` |
| 未决项 | `Documentation/Modules/<模块>.md` |
| 流程与命令层面的坑 | `Documentation/Workflow.md` |
| 会出事的规则（「一律」「不得」） | `CLAUDE.md` |

审计轮**只产出清单，不动代码**。范围由人圈定后才进「计划 → 逐提交实现 → 提交」。

## 六、已知边界

- **IMGUI 渲染结果无法有意义地断言。** 伪造 GUI 上下文只会得到「测试断言了自己的 mock」。
  对策是架构性的而非测试性的：绘制器只做「画 + 调下一个」，一切决策挪进可无头测试的
  代码。审计时若发现某判断只存在于绘制器里，那就是缺陷。
- **`check-docs.ps1` 需要 `.csproj`**，而它只在 GUI 编辑器里生成。纯批处理环境跑不了，
  脚本会正确地判失败而不是给假绿。见 [Workflow.md](Workflow.md) §一。
- **Editor 侧无法离线测试。** `Tests.Native` 只覆盖 Runtime。
- 本手册的清单会随每轮审计新增类别，**别记条数**。
